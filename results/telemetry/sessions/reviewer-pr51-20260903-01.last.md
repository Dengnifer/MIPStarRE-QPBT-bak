## Review

The shared-store direction is reasonable, but the current lifecycle does not preserve package-key isolation.

F1 is caused by the unconditional `return 0` after the mismatch warning. The link must be accepted only when it names the expected, existing store; otherwise it must be replaced or the correct key materialized.

F2 remains even after F1 is fixed: CI invokes `warm-worktree.sh` only when `.lake/build` is absent, then trusts any package symlink. A manifest-changing commit in an already-built worktree therefore bypasses re-keying. CI must validate package linkage unconditionally before building.

For F3, two processes can both pass `[ ! -d "$store" ]`. Once one publishes, the other `mv ... "$store"` treats the existing store as a directory and moves its 7.3 GB staging tree inside it. Publication also masks failures at line 524 and can strand the source after its first move. Use a per-key lock or an atomic no-clobber protocol with cleanup and failure propagation.

F4 should reuse `sha256_stdin` and validate a 16-hex-character result. The current command substitution hides `sha256sum` failure behind successful `printf`.

For F5, `cache-warmer.sh` still fetches into `HOT_REPO/.lake/packages`; when seeded from the migrated primary checkout, that path may itself be the shared symlink. Integrate the producer into key rotation/publication and update the remaining old-topology comments.

`bash -n`, `git diff --check`, and the help path pass. Runtime mutation tests were not run in this read-only review.
